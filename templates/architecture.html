Stage Reference

Detailed breakdown of each pipeline stage.

01

Upload

The file is read into a secure memory buffer via Django's InMemoryUploadedFile. It is never persisted to disk before hashing.

multipart/form-data Django FileField
02

SHA-256 Hash

A 256-bit digest of the raw file is computed with Python's hashlib. Used as a deduplication key and as input to XOR key generation.

hashlib.sha256 64-char hex
↔

Deduplication Check

The SHA-256 fingerprint is queried against the PostgreSQL ledger. If a match is found, only file ownership metadata is updated — no re-encryption occurs.

Unique → Encrypt Duplicate → Return
03

Dynamic Key (XOR)

The AES key is derived by XOR-ing the current file's SHA-256 hash with the previous block's hash. Each file receives a cryptographically unique key — no static secret exists.

XOR synthesis 256-bit key
04

AES-256-GCM

The file is encrypted using AES-256 in GCM mode with a randomly generated 96-bit nonce. GCM produces both ciphertext and a 128-bit authentication tag, ensuring authenticity.

cryptography lib GCM auth tag 96-bit nonce
05

Chunking

The encrypted binary is split into 1 KB (1024-byte) chunks. Each chunk is independently SHA-256 hashed to become a leaf node in the Merkle Tree.

1024-byte blocks Leaf hash per chunk
06

Enhanced Merkle Tree

Leaf hashes are combined pairwise (SHA-256 of concatenation) and propagated upward level by level. The final single hash is the Merkle Root — a tamper-proof fingerprint of the entire ciphertext.

Merkle Root Bottom-up build
07

Hybrid Storage

DB Ledger (PostgreSQL)

Merkle Root, file hash, prev-block hash, and metadata are written to the Supabase PostgreSQL ledger. This forms the immutable blockchain-style chain of blocks.

Object Vault (Supabase Storage)

The binary ciphertext (.bin) — containing the nonce prefix and GCM tag suffix — is stored in the cloud object bucket. Only the Merkle Root is needed to verify it.
